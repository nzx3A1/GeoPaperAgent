# GeoPaper Agent 前后端架构开发方案

## 一、系统建设目标

系统面向地质科研人员，主要处理 PDF 格式的地质论文，完成四个业务闭环：

1. 论文上传、解析、分类和管理；
2. 单篇论文精读与证据问答；
3. 多篇论文专题研究与观点对比；
4. 地质数据批量抽取、审核和导出。

系统必须保证每个重要结论都能追溯到：

```text
论文 → 章节 → 页码 → 原文段落/表格/图片 → 分析结论
```

第一版不建议把知识图谱做成系统中心。Neo4j 主要用于地层层级、区域隶属、井—层位—岩性等关系扩展；正文检索仍以 PostgreSQL、Milvus 和原始证据库为核心。

# 三、开发架构原则

## 1. 第一版采用模块化单体

第一版后端仍然是一个 FastAPI 工程

## 2. 长耗时任务全部异步化

以下操作不能在 HTTP 请求中同步等待：

* PDF解析；
* OCR和表格识别；
* 图片分类与VLM分析；
* Embedding生成；
* 批量论文抽取；
* 多论文专题研究；
* Word、Excel报告生成。

FastAPI 自带的 `BackgroundTasks` 更适合小型后台操作；官方文档明确建议重计算和跨进程任务使用 Celery 等任务队列。Celery通过 Broker将任务分发到一个或多个 Worker，能够扩展到多进程和多服务器。

因此采用：

```text
FastAPI：接收请求、创建任务、立即返回 task_id
Redis：Broker、缓存、任务进度
Celery Worker：执行解析、检索、抽取和报告任务
PostgreSQL：保存任务状态和业务结果
SSE：向前端推送进度
```

## 3. 确定性流程与 Agent 分离

不能让大模型控制所有步骤。

确定性流程负责：

* PDF页码处理；
* 文件哈希去重；
* 坐标转换；
* 表格结构装配；
* 数据单位换算；
* 数据库写入；
* 引用格式生成；
* 权限和文件操作。

Agent负责：

* 理解研究问题；
* 拆解研究维度；
* 判断调用哪些工具；
* 判断证据是否充分；
* 比较论文观点；
* 生成带证据的结论。

LangGraph适合在同一流程中混合确定性节点与LLM驱动节点，并提供状态持久化、流式输出和人工审核能力。

# 四、前端架构设计

## 1. 前端技术栈

| 分类       | 建议技术                  |
| -------- | --------------------- |
| 核心框架     | Vue 3、TypeScript、Vite |
| 状态管理     | Pinia                 |
| 路由       | Vue Router            |
| UI组件     | Element Plus或Naive UI |
| PDF阅读    | PDF.js                |
| 图表展示     | Apache ECharts        |
| 请求管理     | Axios                 |
| 流式通信     | SSE，必要时补充WebSocket    |

ECharts适合展示参数分布、论文统计、研究趋势、地质参数箱线图和抽取质量统计。

## 2. 页面结构

### 项目工作台

展示：

* 项目论文数量；
* 已解析、解析中、解析失败数量；
* 最近研究任务；
* 已构建数据集；
* 论文年份、研究区域、研究层位统计；
* 最近生成的研究报告。

### 论文库页面

支持：

* 批量上传PDF；
* 文件夹和标签管理；
* 按盆地、地区、层位、年份、作者筛选；
* 解析状态查看；
* 重复论文检测；
* 批量重新解析；
* 批量加入专题研究。

### 论文阅读页面

建议使用三栏布局：

```text
┌────────────┬──────────────────────┬────────────────┐
│ 章节目录    │ PDF原文              │ AI分析与证据    │
│            │                      │                │
│ 摘要        │ 当前页               │ 结构化摘要      │
│ 方法        │ 高亮证据             │ 问答            │
│ 结果        │ 表格/图片标注        │ 关键参数        │
│ 结论        │                      │ 图表解释        │
└────────────┴──────────────────────┴────────────────┘
```

前端必须支持点击AI结论后：

1. 自动跳转到对应页；
2. 高亮对应文本区域；
3. 展示原始段落；
4. 展示图号、表号和证据类型；
5. 标记“原文证据”和“模型解释”的边界。

### 专题研究页面

页面分为四部分：

```text
研究问题
   ↓
Agent执行计划
   ↓
论文和证据列表
   ↓
专题结论与报告
```

需要展示每个Agent步骤：

```text
✓ 分析研究问题
✓ 拆分研究维度
✓ 检索相关论文 38篇
✓ 筛选核心证据 126条
● 正在比较争议观点
○ 等待生成报告
```

不要把模型的完整思维过程直接展示给用户，只展示：

* 当前步骤；
* 使用了什么工具；
* 检索了哪些论文；
* 找到多少证据；
* 为什么需要补充检索；
* 最终采用和排除哪些证据。

### 数据抽取页面

采用“字段模板 + 数据表格 + 原文证据”布局：

```text
抽取模板：
井号、研究区、层位、深度、岩性、TOC、Ro、孔隙度、渗透率

结果表：
论文 | 井号 | 层位 | TOC | Ro | 证据 | 审核状态
```

每条数据支持：

* 查看原文；
* 修改字段；
* 确认；
* 驳回；
* 标记单位错误；
* 标记实体对应错误；
* 批量导出Excel或CSV。

## 3. 前端状态管理

建议拆分以下Pinia Store：

```text
authStore
projectStore
paperStore
viewerStore
taskStore
researchStore
extractionStore
reportStore
```

其中 `taskStore` 统一管理所有异步任务：

```typescript
interface TaskState {
  id: string
  type: string
  status: 'pending' | 'running' | 'success' | 'failed' | 'cancelled'

  currentStep: string
  message?: string

  error?: string
}
```

避免每个页面单独实现进度条、轮询和错误提示。

# 五、后端服务设计

## 1. API层

FastAPI主要负责：

* 身份认证；
* 项目权限；
* 参数校验；
* 文件上传签名；
* 创建后台任务；
* 查询任务状态；
* 查询分析结果；
* 报告下载；
* SSE连接。

API层不能直接调用耗时模型。

## 2. 论文管理模块

职责：

```text
创建论文记录
生成上传地址
计算文件SHA-256
检查重复文件
读取论文元数据
维护论文版本
管理解析状态
删除和恢复论文
```

论文状态建议：

```text
UPLOADING
UPLOADED
QUEUED
PARSING
INDEXING
READY
PARTIAL_SUCCESS
FAILED
```

`PARTIAL_SUCCESS`非常重要。例如正文解析成功，但某两张复杂表格识别失败，不能把整篇论文标记为完全失败。

## 3. 文档解析模块

完整流程：

```text
PDF上传
  ↓
文件校验与去重
  ↓
MinerU解析
  ↓
生成Markdown和版面数据
  ↓
章节树重建
  ↓
正文、表格、图片、公式分流
  ↓
Chunk切分
  ↓
地质图件分类
  ↓
表格和图片专项解析
  ↓
Embedding生成
  ↓
写入数据库与检索库
  ↓
质量检查
```

解析产物统一保存：

```text
papers/{paper_id}/
├── original.pdf
├── full.md
├── section_tree.json
├── layout.json
├── content_list.json
├── chunks/
├── tables/
├── images/
├── formulas/
└── parse_manifest.json
```

其中 `parse_manifest.json` 记录：

```json
{
  "parser_version": "v1.0",
  "page_count": 18,
  "section_count": 23,
  "text_chunk_count": 156,
  "table_count": 8,
  "image_count": 12,
  "failed_assets": [],
  "started_at": "",
  "finished_at": ""
}
```

## 4. 检索模块

建议采用多路召回：

```text
问题
 ├─ Dense向量召回
 ├─ Sparse关键词召回
 ├─ PostgreSQL条件过滤
 ├─ 地质实体扩展
 ├─ 章节优先级召回
 └─ 图谱关系扩展
          ↓
       融合排序
          ↓
       Reranker
          ↓
       证据集合
```

Milvus支持Dense、Sparse和Hybrid检索，因此适合地质论文中“专业关键词匹配 + 语义相似度”并用的场景。

建议检索对象不是只有普通文本Chunk，而是：

```text
TextChunk
TableChunk
ImageChunk
FormulaChunk
ConclusionChunk
```

每条索引必须包含过滤字段：

```json
{
  "project_id": "",
  "paper_id": "",
  "chunk_id": "",
  "modality": "text",
  "page_start": 8,
  "page_end": 8,
  "section_path": "结果/储层特征/孔隙结构",
  "basin": "鄂尔多斯盆地",
  "formation": "延长组",
  "member": "长7段",
  "year": 2024
}
```

## 5. Agent服务

建议设置三种Agent，而不是一个万能Agent。

### PaperReader Agent

负责单篇论文：

```text
论文结构理解
关键结论提取
图表解释
证据问答
方法与局限分析
```

### TopicResearch Agent

负责跨论文：

```text
问题拆解
多轮检索
证据聚合
论文观点比较
冲突分析
研究空白发现
专题报告生成
```

### DataExtraction Agent

负责结构化数据：

```text
理解抽取Schema
选择相关章节和表格
提取字段
单位归一化
实体对齐
质量检查
提交人工审核
```

# 六、Agent工作流设计

## 1. 专题研究Agent状态

```python
class ResearchState:
    task_id: str
    project_id: str
    question: str

    research_dimensions: list
    retrieval_queries: list
    candidate_papers: list
    evidence_items: list

    accepted_evidence: list
    rejected_evidence: list
    evidence_gaps: list

    findings: list
    conflicts: list
    report_sections: list

    current_step: str
    iteration: int
    warnings: list
```

## 2. Agent节点

```text
START
  ↓
understand_question
  ↓
build_research_plan
  ↓
retrieve_papers
  ↓
retrieve_evidence
  ↓
rank_and_filter
  ↓
analyze_evidence_gaps
  ├─ 证据不足 → generate_followup_queries
  │               ↓
  │            retrieve_evidence
  │
  └─ 证据充分
          ↓
compare_viewpoints
          ↓
generate_findings
          ↓
verify_citations
          ↓
generate_report
          ↓
END
```

## 3. Agent工具

```text
search_papers()
search_chunks()
search_tables()
search_figures()
get_paper_outline()
get_page_evidence()
get_entity_relations()
compare_numeric_parameters()
normalize_geology_term()
normalize_unit()
create_dataset()
generate_report()
```

Agent不能直接执行任意SQL、Shell或文件删除操作。所有工具必须通过受控接口注册。

## 4. 证据校验

生成结论前执行以下检查：

```text
结论是否至少绑定一条证据
证据是否属于当前项目
页码是否存在
引用文本是否真实存在
图号和表号是否匹配
数值和单位是否一致
论文观点是否被过度概括
多个论文是否被错误合并
```

建议为每条结论保存：

```json
{
  "claim": "长7段优质烃源岩主要发育于半深湖—深湖相",
  "confidence": 0.87,
  "evidence_ids": ["ev_001", "ev_016", "ev_038"],
  "supporting_paper_count": 3,
  "conflicting_evidence_ids": ["ev_042"],
  "status": "verified"
}
```

## 4. Neo4j设计


关系示例：

```text

(Paper)-[:MENTIONS]->(Entity)
(Evidence)-[:SUPPORTS]->(Relation)
```

Neo4j使用节点、关系和属性表达关联数据，适合地层层级和跨论文实体关系遍历。

第一版可以暂时不部署Neo4j，先在PostgreSQL中保存实体和关系，等专题检索闭环稳定后再引入。

# 九、异步任务队列设计

按照资源类型拆分队列：

```text
paper_parse_cpu
paper_parse_gpu
image_understanding_gpu
embedding_gpu
agent_llm
data_extraction
report_export
```

不同Worker独立设置并发数：

```text
CPU解析Worker：并发4～8
OCR Worker：并发2～4
VLM Worker：根据GPU显存设置
Embedding Worker：批量处理
Agent Worker：限制每用户并行任务数
报告导出Worker：并发2～4
```

任务必须支持：

* 幂等执行；
* 自动重试；
* 超时；
* 取消；
* 断点恢复；
* 失败步骤重跑；
* 子任务进度统计。

例如论文解析过程不能只保存最终结果，应保存每个阶段状态：

```text
pdf_validate        SUCCESS
mineru_parse        SUCCESS
section_build       SUCCESS
table_parse         PARTIAL_SUCCESS
image_parse         RUNNING
embedding           PENDING
```

# 十、文件与数据流

## 论文上传数据流

```text
前端申请上传地址
  ↓
后端创建paper记录
  ↓
前端直接上传MinIO
  ↓
后端确认上传完成
  ↓
创建解析任务
  ↓
Worker从MinIO读取PDF
  ↓
解析产物重新写入MinIO
  ↓
元数据写入PostgreSQL
  ↓
向量写入Milvus
  ↓
论文状态更新为READY
```

前端直接上传对象存储，可以避免几个GB文件经过FastAPI进程中转。

```text

  ↓

  ↓
Agent生成研究计划
  ↓
调用检索服务
  ↓
取得多模态证据
  ↓
进行证据筛选和缺口分析
  ↓
必要时追加检索
  ↓
生成观点、冲突和结论
  ↓
引用检查
  ↓
保存报告
  ↓
SSE通知前端完成
```

# 十一、权限与安全

至少需要实现：

| 安全能力       | 实现方式                 |
| ---------- | -------------------- |
| 项目隔离       | 所有数据查询强制携带project_id |
| 文件隔离       | MinIO对象路径按项目划分       |
| 下载控制       | 使用限时签名URL            |
| 接口权限       | JWT + RBAC           |
| Agent工具权限  | 工具白名单                |
| 数据删除       | 软删除 + 审计日志           |
| 模型调用       | 脱敏、日志分级              |
| Prompt注入防护 | 论文内容仅作为数据，不作为系统指令    |
| 任务限制       | 用户并发、Token、文件大小配额    |
| 操作审计       | 上传、删除、导出、修改均记录       |

论文中的文字可能包含“忽略之前指令”等内容，因此检索到的论文内容必须被包裹为不可执行的证据数据，不能直接拼接为Agent系统指令。

# 十八、最重要的开发取舍

第一版应当优先完成：

```text
论文上传
→ 稳定解析
→ 原文证据定位
→ 混合检索
→ 专题研究
→ 结构化数据导出
```

暂时不要优先投入：

```text
复杂知识图谱可视化
全自动科研结论发现
大量子Agent
复杂微服务拆分
支持所有地质图件
自动操作任意本地软件
```

真正决定系统价值的不是Agent界面有多复杂，而是：

1. 能否准确找到论文证据；
2. 能否定位到正确页码和图表；
3. 能否区分原文事实与模型推断；
4. 能否对多篇论文进行可靠比较；
5. 能否将结果转化成可审核的数据和报告。
