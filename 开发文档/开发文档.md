# GeoAgent 地质盆地专题科研智能助手开发文档

## 1. 项目概述

### 1.1 项目名称

**GeoAgent——面向含油气盆地专题研究的地质科研智能助手**

### 1.2 项目背景

项目已有一个由团队成员预先构建的地质论文资源库，通过论文爬虫长期收集国内外石油地质、沉积学、地层学、储层地质学等方向论文，累计形成**数万篇含油气盆地相关论文**。

论文主要涉及：

* 鄂尔多斯盆地
* 四川盆地
* 塔里木盆地
* 准噶尔盆地
* 松辽盆地
* 渤海湾盆地
* 柴达木盆地
* 珠江口盆地

以及盆地内部的地层、沉积体系、储层、烃源岩、成藏条件等专题。

传统科研过程中，研究人员完成一个类似：

> **“鄂尔多斯盆地延长组长7段沉积环境及沉积模式研究”**

的专题，需要人工完成：

```text
检索大量相关论文
        ↓
筛选高相关文献
        ↓
逐篇阅读正文
        ↓
寻找相关章节
        ↓
整理地层、沉积相、岩性等信息
        ↓
分析论文中的表格和地质图件
        ↓
对不同论文结论进行归纳
        ↓
记录引用来源
        ↓
组织研究逻辑
        ↓
撰写专题研究报告
```

即使论文已经全部下载，本质问题仍然没有解决：

> **论文很多，但研究人员仍然需要人工完成“检索—阅读—分析—综合—验证—写作”。**

因此项目目标并不是简单实现一个“论文问答 RAG”，而是开发一个能够围绕**具体石油地质科研任务自主工作的 Research Agent**。

---

# 2. 项目定位

GeoAgent 的核心定位为：

> **以数万篇地质论文为知识基础，让 Agent 围绕一个地质专题自主完成研究任务规划、资料检索、论文解析、多模态分析、证据核验、Python 数据分析及专题报告生成。**

系统主要面向：

* 石油地质
* 沉积学
* 地层学
* 储层地质学
* 构造地质学
* 油气成藏研究

而不是做开放领域科研 Agent。

这种领域限制可以显著提高：

* 检索准确率
* 专业术语理解能力
* Prompt 稳定性
* 报告结构一致性
* 证据可验证性

# 8. Agent 状态结构

为了避免完全依靠对话历史驱动 Agent，我将任务状态结构化。

例如：

```python
class AgentState(BaseModel):

    research_topic: str

    research_goal: str

    plan: list[ResearchTask]

    current_task: int

    completed_tasks: list[str]

    pending_tasks: list[str]

    evidence: list[Evidence]

    artifacts: list[Artifact]

    observations: list[str]

    errors: list[str]

    iteration: int
```

其中核心不是完整保存所有 LLM 对话，而是保存：

```text
任务状态
+
研究计划
+
已经完成的工作
+
关键研究发现
+
关键证据
+
成果文件
```

这样长任务执行更加稳定。

# 10. 动态计划调整

Research Agent 与固定 Workflow 最大的区别之一，是任务计划允许在执行过程中调整。

例如 Agent 最初认为主要需要研究：

```text
沉积环境
沉积相
物源
```

但执行论文分析后发现：

> “湖平面变化是控制长7沉积体系的重要因素。”

Agent 可以增加任务：

```text
T09
分析长7时期湖平面变化及其对沉积体系的控制
```

形成：

```text
Planner
   ↓
Executor
   ↓
发现新的研究问题
   ↓
Reflector
   ↓
Update Plan
   ↓
继续研究
```

# 11. 科研工具体系

为了避免 LLM 自己完成所有任务，将科研能力封装成标准 Tool。

整体 Tool 分为六类。

| Tool 类型         | 主要功能           |
| --------------- | -------------- |
| Retrieval Tools | 查找论文、章节、Chunk  |
| Document Tools  | 读取 PDF、正文、表格   |
| Image Tools     | 分析柱状图、剖面图、沉积相图 |
| Analysis Tools  | Python 数据分析与统计 |
| Workspace Tools | 文件、研究结果管理      |
| Report Tools    | 报告、表格及成果导出     |

共封装 **15+ Agent Tools**。

例如：

```python
search_papers(
    query="鄂尔多斯盆地 长7 沉积相",
    top_k=20
```

返回：

```json
[
  {
    "paper_id": "P10231",
    "title": "...",
    "authors": "...",
    "year": 2021,
    "score": 0.91
  }
]
```

```python
search_sections(
    paper_id="P10231",
    query="沉积环境"

```

# 13. 多级检索

由于数据库中存在数万篇论文，不能直接对所有 Chunk 做简单 TopK。

设计为：

```text
用户研究问题

        ↓

论文级召回

        ↓

筛选相关论文

        ↓

章节级召回

        ↓

Chunk级精细检索

        ↓

Cross Encoder / LLM Rerank

        ↓

Evidence
```

例如：

```text
查询：
长7沉积环境

论文级：
10000+论文
 ↓
Top 100

章节级：
约1000个相关章节
 ↓
Top 50

Chunk级：
 ↓
Top 20

最终Evidence：
 ↓
5~10条
```

这样可以减少大量无关文本进入 LLM。

# 14. 论文解析

论文进入系统以后首先经过 MinerU 解析。

```text
PDF
 │
 ▼
MinerU
 │
 ├── Title
 ├── Abstract
 ├── Section
 ├── Paragraph
 ├── Table
 ├── Figure
 └── Caption
```

随后重新构建论文结构：

```text
Paper
 │
 ├── Abstract
 │
 ├── 1 Geological Background
 │
 ├── 2 Stratigraphy
 │
 ├── 3 Sedimentary Characteristics
 │      │
 │      ├── 3.1 Sedimentary Facies
 │      ├── Figure 5
 │      └── Table 2
 │
 ├── 4 Discussion
 │
 └── Conclusion
```

这样检索结果不仅有文本，还知道：

> **来自哪篇论文、哪个章节、哪一页、哪张图。**

# 15. Chunk 设计

普通固定长度 Chunk 会破坏地质论文语义。

因此使用：

> **章节结构优先 + Token 长度约束**

例如：

```text
Paper
  ↓
Section
  ↓
Subsection
  ↓
Paragraph Group
  ↓
Chunk
```

Chunk Metadata 保存：

```json
{
  "paper_id": "P10231",
  "section": "3.2 沉积相特征",
  "page": 8,
  "figure_refs": ["Fig5"],
  "chunk_text": "..."
}
```

从而保证引用信息不会丢失。

# 17. 地质图件分析

例如论文中存在：

> 长7时期沉积相平面分布图

VLM 不只是简单描述：

> “这是一张沉积相图。”

而是要求按照地质 Schema 抽取：

```json
{
  "basin": "鄂尔多斯盆地",
  "formation": "延长组",
  "member": "长7",
  "figure_type": "沉积相平面图",

  "facies": [
    "三角洲前缘",
    "深湖",
    "半深湖"
  ],

  "features": [
    "砂体主要沿东北—西南方向展布"
  ]
}
```

这些结构化结果可以作为 Agent 后续分析的 Observation。

# 19. Evidence 证据模型

这是整个科研 Agent 非常重要的设计。

系统要求：

> **重要研究结论必须关联 Evidence。**

Evidence 数据结构：

```python
class Evidence(BaseModel):

    evidence_id: str

    paper_id: str

    paper_title: str

    section: str

    page: int

    content: str

    evidence_type: str

    figure_id: str | None

    confidence: float
```

例如：

```json
{
  "evidence_id": "E001",
  "paper_id": "P10231",
  "section": "3.2 沉积相",
  "page": 8,
  "content": "研究区长7主要发育...",
  "evidence_type": "text",
  "confidence": 0.92
}
```

> **Claim → Evidence**

# 21. 多论文观点融合

科研研究不能把所有论文结论简单拼接。

Agent 需要识别：

```text
一致观点
少数观点
冲突观点
不同研究区导致的差异
不同数据导致的差异
```

例如：

```text
论文A：
长7主要发育深湖—半深湖沉积

论文B：
长7东北部存在明显三角洲前缘沉积

论文C：
长7沉积体系受到东北部物源控制
```

Agent 最终组织为：

> 长7整体表现为深湖—半深湖环境，但盆地东北部和局部缓坡区仍广泛发育三角洲前缘沉积体系，多数研究认为其展布与东北方向物源供给密切相关。

并保留三个结论各自对应的论文证据。

# 22. Evidence Verification

报告生成前增加一次独立核验。

Verifier 检查：

```text
① 结论是否存在证据

② Evidence 是否真的支持 Claim

③ 地层是否对应

④ 盆地是否对应

⑤ 地质年代是否混淆

⑥ 数值是否与论文一致

⑦ 是否将不同研究区结论错误合并
```

例如：

```json
{
  "claim": "长7主要为深湖沉积",

  "status": "SUPPORTED",

  "evidence_count": 4,

  "confidence": 0.91
}
```

证据不足时：

```json
{
  "status": "INSUFFICIENT_EVIDENCE"
}
```

Agent 可以重新进入 Retrieval 阶段。

因此形成：

```text
Generate Claim
      ↓
Verify Evidence
      ↓
Enough?
 ┌────┴────┐
 No        Yes
 │          │
 ▼          ▼
Search    Report
Again
```

# 24. Tool 安全机制

因为 Agent 可以运行 Python / Bash，因此不能让模型直接操作服务器所有路径。

增加：

### 路径白名单

例如：

```text
/workspace/{task_id}/
```

Agent 只能访问当前任务目录。

### 超时

```text
Python：120s

Bash：60s
```

### Tool 参数校验

使用 Pydantic：

```python
class PythonToolArgs(BaseModel):

    script: str

    timeout: int = 120
```

### 统一 Tool Result

```json
{
  "success": true,
  "output": "...",
  "error": null,
  "artifacts": []
}
```

因此 Agent 可以统一处理工具失败。

# 25. Tool Failure Retry

例如：

```text
Agent调用Python
        ↓
执行失败
        ↓
Observation:
Column "TOC" does not exist
        ↓
Reflection
        ↓
重新读取CSV字段

```

避免一次 Tool Error 导致整个研究任务失败。

这也是：

> **规划—执行—观察—修正**

闭环的一部分。

# 26. 长上下文优化

长科研任务可能执行几十次 Tool Calling。

如果简单把历史全部传给 LLM：

```text
System
User
Tool
Tool Result
Assistant
Tool
Tool Result
...
```

Token 会快速增长。

因此对 Context 进行阶段性压缩。

---

# 27. Context 分层

保留四类信息：

```text
Agent Context

├── Research Goal
│
├── Current Plan
│
├── Research Memory
│
├── Evidence
│
└── Recent Tool Results
```

历史 Tool Result 不长期保留完整内容。

例如原始 Tool Output：

```text
10,000 Token
```

被压缩成：

```text
发现：
1. 长7主要发育深湖—半深湖沉积
2. 东北方向存在明显物源输入
3. 检索到相关论文17篇

Evidence:
E001
E004
E008
```

只保存后续研究需要的信息。

在真实长任务测试中，通过这种方式使平均 Token 消耗降低约：

> **35%**

# 28. Research Memory

长期研究过程中形成：

```json
{
  "known_facts": [],
  "hypotheses": [],
  "confirmed_findings": [],
  "conflicting_findings": [],
  "evidence_ids": []
}
```

例如：

```text
Known Fact

长7属于延长组重要沉积层段

Confirmed Finding

长7沉积期大范围发育湖相环境

Hypothesis

东北方向物源可能控制砂体展布

Need Evidence

湖平面升降与砂体展布关系
```

Planner 可以据此决定下一步做什么。

# 29. 科研报告生成

最终结果不是普通聊天回答，而是一份结构化专题研究报告。

例如：

# 鄂尔多斯盆地延长组长7段沉积环境研究

## 1 研究背景

介绍：

* 鄂尔多斯盆地
* 延长组
* 长7地层背景
* 研究意义

---

## 2 区域地质背景

整理：

# 45. 最终项目本质

这个项目最准确的描述不是：

> “做了一个地质 RAG。”

也不是：

> “做了一个论文问答系统。”

而是：

> **基于已有数万篇地质盆地论文库，开发面向石油地质专题研究的 Research Agent，将科研过程拆解为规划、检索、论文解析、多模态分析、数据处理、证据核验和报告生成，并通过 Tool Calling 自主执行完整研究流程。**

例如：

```text
“鄂尔多斯盆地延长组长7段沉积环境研究”

并不是一次LLM问答

而是：

研究问题
   ↓
Agent Planning
   ↓
数万篇论文检索
   ↓
相关论文筛选
   ↓
相关章节定位
   ↓
正文 / 表格 / 地质图件分析
   ↓
多论文观点融合
   ↓
Evidence Verification
   ↓
科研结论
   ↓
专题研究报告
```

这也能很好地解释你简历里为什么会同时出现 **Agent Loop、RAG、MinerU、VLM、Pydantic、Python/Bash Tool、Evidence Tracking 和 Research Report Generation**：它们不是为了堆技术栈，而是分别对应真实科研流程中的一个环节。
